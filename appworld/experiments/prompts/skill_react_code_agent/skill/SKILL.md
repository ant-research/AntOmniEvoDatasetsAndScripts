## Overview
Complete AppWorld tasks by writing Python code that calls app APIs, follows pagination, and returns correct answers or performs actions without returning unnecessary answers.

## Procedure
1. Read the task instruction. Determine whether it asks a QUESTION (needs an answer) or requires an ACTION (no answer needed). See Output Format for the decision procedure.
2. Look up credentials via `apis.supervisor.show_account_passwords()` and personal info via `apis.supervisor.show_profile()`. Always call both — `show_profile()` provides the email and phone_number needed as login usernames; `show_account_passwords()` provides the passwords. Never guess or hardcode login usernames or passwords. Extract values programmatically and USE them in subsequent calls: `email = profile['email']`, `phone = profile['phone_number']`, `pw = next(p['password'] for p in passwords if p['account_name'] == 'venmo')`; then `apis.venmo.login(username=email, password=pw)` — pass the variable, not the literal string. Hardcoding transcribed values is fragile: special characters mangle on copy-paste, and credential values change across instances. Login to EVERY app you will use before calling its APIs — if step 1 identifies that the task needs Venmo and Phone, login to both before proceeding to step 3. If the task mentions a social relationship qualifier ('friends', 'roommates', 'coworkers', 'family'), the Phone app is always needed to resolve the relationship — include it in the login list even if all task actions occur in another app. Forgetting to login causes NameError on access_token when the API call is attempted.
3. Before writing any task-logic code, enumerate ALL APIs for EVERY task step — including mutation APIs (create, update, delete, add, remove) and detail-fetch APIs (show_<entity> for individual records), not just collection/search APIs. Then read `references/api-discovery.md` and execute its code pattern — call `show_api_doc` for every enumerated API in a separate code block before the implementation code block. This is NOT optional — it is the FIRST code block after login. Agents typically check only collection APIs and forget to verify mutation/detail-fetch APIs, assuming their parameters are obvious — but parameter names routinely differ from expectations (e.g., `login` takes `username` not `email`, response fields use `id` not `song_id`), and `show_` APIs can return paginated lists just like `list_`/`search_` APIs. Never write an implementation code block until the API doc code block has been executed and its output read. If an API's doc shows it accepts `page_index`/`page_limit`, plan to paginate per `references/pagination.md`. Use filter parameters (genre, query, etc.) on search APIs to narrow results instead of fetching all records.
4. Implement the task logic using the verified API signatures. For any API that accepts `page_index`/`page_limit` (identified in step 3), include `page_index=0` and `page_limit=20` in the VERY FIRST call and loop through all pages — never call a collection API without pagination parameters first and then try to 'add pagination later' starting from page 1. A non-paginated first call returns a different (smaller) result set than page_index=0 with page_limit=20, so building on it and paginating from page 1 produces incomplete data. Always start the pagination loop from scratch at page_index=0. If step 3's API doc check shows the API does not accept page_index/page_limit, no pagination is needed — but confirm via the doc, not by assuming. If the task involves looking up an entity by name and then fetching or acting on its related items (songs by an artist, products by a seller, etc.), read `references/workflows.md` for the integrated code template that combines entity lookup, paginated fetching, ID extraction, and filtering into a single correct flow. Self-check gate: after every collection API call, verify all three: (1) `page_index` and `page_limit` were included — if not, discard and re-fetch with `page_index=0, page_limit=20` plus a pagination loop; the un-paginated default silently omits items. (2) The pagination loop ran until `len(batch) < 20` — a lone `page_index=0` call misses items beyond page 0. (3) Any ID or value used in a subsequent API call was extracted from a stored variable (e.g., `note_id=next(n['note_id'] for n in notes if 'Workout' in n['title'])`), not typed as a literal copied from printed output — literals from printout break when results change across pages or runs.
Social relationship gate: if the task qualifies an action by a social relationship ('friends', 'roommates', 'coworkers', etc.), resolve the allowed person set via `phone.search_contacts(relationship='<type>')`, paginating through all pages — never use app-specific social APIs (e.g., `venmo.search_friends`) which return platform connections, not relationship-labeled contacts. Extract the allowed email set programmatically and use it to filter results.
Additionally, before calling any create/update/delete API (download, follow, create_review, etc.), query the current state via a show/list/detail API to determine which target entities already exist — skip entities already in the desired state to avoid 422 duplicate errors. Downloading an already-downloaded song or creating a second review crashes the code block and wastes recovery steps.
5. Verify the result: re-query the changed state to confirm the action took effect, or re-check counts before reporting an answer. Re-queries are collection API calls too — if the API accepts `page_index`/`page_limit`, include them and use a pagination loop per `references/pagination.md`, exactly as in step 4. A non-paginated verification can return a truncated result set that makes a partial change appear complete, causing premature `complete_task` calls. When the task says some people have already done something (e.g., 'some have already paid', 'already sent me'), read `references/action-verification.md` and follow its code pattern — never use `query=` keyword search; always fetch with structural filters and match by identity AND amount in code. Do not call `complete_task` until verification passes.
6. Call `apis.supervisor.complete_task()` with the correct arguments per Output Format below.

## Rules
- Paginated APIs: always use a pagination loop with `page_limit=20` (larger causes 422 errors). Never fetch only `page_index=0` — loop while `len(batch) == 20`, incrementing `page_index` each iteration. Collect all pages before filtering or acting on results. Read `references/pagination.md` for the full code template.
- Use filter parameters on search and collection APIs (e.g., `genre="EDM"`) to narrow results instead of fetching all records and filtering manually. For time-bounded queries ("this month", "last week"), compute `min_created_at`/`max_created_at` from the current date and pass them as API parameters — `show_`/`list_` APIs also support date range filters, not just `search_` APIs. Check the API doc to see which filters are available.
- Apply numeric thresholds (e.g., "at least 23 followers") by first checking via show_api_doc whether the API supports a filter parameter for that threshold. If it does, use the filter parameter — it is more efficient and avoids fetching unnecessary data. If it does not, apply the threshold as a code comparison on the API results. Never use an unverified filter parameter — guessing causes 422 errors or silent wrong results.
- For library/collection cleanup tasks, compute the set of items to keep vs. remove using set operations before deleting. Use intersection (`&`) when the task requires items satisfying ALL conditions (e.g., 'liked AND downloaded'), and union (`|`) when items satisfying ANY condition should be kept. Always re-read the task wording to determine which operation applies.
- When a task says 'X from Y that are/have Z' (e.g., 'songs from my album library that I have liked'), the qualifier Z applies to the items X, NOT to the source collection Y. Fetch each condition's data at the correct entity level and intersect: {items of type X from source Y} ∩ {items of type X satisfying condition Z}. In the example, 'liked' is a per-song property — use `show_liked_songs` to get liked song IDs, not `show_liked_albums`. Applying the qualifier at the wrong entity level (e.g., filtering albums by 'liked' when the task asks for liked songs) returns a different and incorrect result set.
- For superlative questions ("most X", "least X", "top X"), first check whether the API has an explicit ranking or ordering field for that metric — if it does, use it. If not, count programmatically (e.g., for "least recommended," count each artist's appearances across all recommendation results and find the minimum). Counting occurrences in API results is not an "invented metric" — it is the correct method when no ranking field exists. When the task says "the X" (singular) and counting produces ties among the top candidates, verify that all data has been collected (missing pagination pages can cause false ties), then re-examine the API doc for a ranking field or a more-specific endpoint.
- When the task defines a condition on one entity type in terms of another (e.g., 'an album is downloaded if all its songs are downloaded'), derive the condition by fetching related entities and checking membership. Build the derived property set before applying the keep/remove logic.
- When a task requires creating or updating entities (reviews, ratings, settings, follows, downloads, likes, etc.), check the current state of each entity first to determine which operation applies: create (entity doesn't exist yet), update (entity exists but needs modification), or skip (entity already in desired state). Use a show/detail/list API filtered by identity to check existence, then call the appropriate create or update API. Creating a duplicate record (e.g., a second review, downloading an already-downloaded song, liking an already-liked transaction) causes 422 errors or test failures; updating a non-existent record causes errors. Likes are strictly single-state — calling like on an already-liked entity always 422s, so pre-checking is essential.
- When a task references items across multiple collections, libraries, or lists (e.g., 'across my song, album and playlist libraries'), collect from every mentioned source and deduplicate by entity ID. For ID-only tasks (counting, filtering), use set union on IDs — the same entity can appear in multiple collections. Missing a source means missing items; failing to deduplicate means over-counting. For tasks requiring full entity data (export, reporting, CSV generation), use a dict keyed by entity ID: `all_items = {}; for item in source: all_items[item['<id_field>']] = item`. This deduplicates by ID while preserving the full record. When entities from different APIs have different field names for the same data (e.g., 'song_id' vs 'id'), normalize them into a consistent format when inserting: `all_items[song['id']] = {'song_id': song['id'], 'title': song['title'], ...}`. When collecting child entity IDs from multiple parent records (e.g., song_ids from multiple albums), also deduplicate by child entity ID — the same child can belong to multiple parents, and duplicates cause wrong counts or redundant API calls.
- When a list/summary API response lacks a field needed for the task (e.g., release_date missing from library listings), use the individual detail/show endpoint to retrieve that field for each item. Inspect summary output to confirm it contains needed fields before relying on it. Do NOT infer a child entity's property from a parent or related entity (e.g., do not use an album's release_date as a proxy for a song's release_date) — a song may be released as a single before its album, so the dates can differ. If the collection listing lacks the needed property, fetch it from each item's own detail endpoint, even if a related entity appears to provide a similar field.
- Always process structured data programmatically — whether from notes/files/messages or from API responses (transaction records, search results, user lists). Never hardcode values read from printed REPL output into subsequent code. Use regex or string methods to extract name-value pairs. When cross-referencing data across sources (e.g., shares in a note vs. payments in transactions), assign each API response to a variable, then use set/dict operations and the `references/action-verification.md` pattern to match and compute differences. Manual transcription from printed output causes value misassignment. When a task requires processing files or sub-directories from a directory, store the `show_directory` response in a variable and process it programmatically — never manually type file paths or directory names observed in printed output. For filtering files: `[f for f in files if 'internet' in f and '2023' in f and f.endswith('.txt')]`. For extracting sub-directory names: `subdirs = set(p.replace(base_path, '').split('/')[0] for p in listing if p.endswith('/') and p != base_path)` where base_path is the parent directory path used in show_directory.
- Filter out `None` values before passing entity IDs as API parameters — entity ID fields (album_id, artist_id, etc.) can be `None` when the entity has no parent (e.g., songs without albums). Passing `None` as an ID argument causes a 422 validation error. When collecting IDs from API responses into a set or list, exclude None before iterating: `{song['album_id'] for song in songs if song['album_id'] is not None}`.
- When an API response contains entity IDs in nested objects (e.g., `artist_id` within a song's `artists` list, `seller_id` within an order's items), extract those IDs directly — do not call a separate search API to resolve names to IDs. Search uses fuzzy matching and may return wrong entities when names are shared or partially match, causing wrong-entity operations. Example: from `song['artists']`, collect `artist['artist_id']` directly rather than searching `search_artists(query=artist['name'])`.
- Never invent or guess values. Look up credentials and personal info from supervisor APIs.
- When the task references a prior communication (e.g., 'reply to them', 'as per their request', 'their message'), read that communication first to extract the specific criteria or question before acting. For example, if asked to reply with recommendations 'as per their request', read the text message or email to find what specifically was requested (e.g., a director name, a genre) and filter accordingly.
- When a task qualifies an action by a social relationship (e.g., 'from my friends', 'by my roommates', 'from my coworkers'), resolve each relationship noun by searching the phone contact book: `apis.phone.search_contacts(access_token=phone_token, relationship='<type>', page_index=0, page_limit=20)` — paginating through all pages. Phone contacts have explicit relationship labels (friend, roommate, coworker, family, etc.) that correspond to the task's qualifiers. Search for EACH relationship type mentioned in the task separately. After collecting all pages, extract the allowed set programmatically: `allowed_emails = {c['email'] for page in all_pages for c in page}`. Never manually list emails from printed output in a subsequent code block — manual transcription omits valid members and adds non-members, producing wrong totals. Venmo's `search_friends` returns platform connections (the Venmo social graph), not relationship-labeled contacts — do NOT use it to determine who counts as 'my friends' or 'my roommates' in the task. For platform-specific social graphs (e.g., 'from my followers', 'by people I follow'), use the relevant app's API (e.g., `show_followers`). Filter actions (deny, delete, send) to only affect items from entities in the combined relationship set. Non-friends/non-roommates can appear in payment requests, messages, etc. — never assume all results satisfy the social qualifier.
- When the task identifies a person by a phone number or email address (e.g., 'the person with this phone number'), resolve their identity via phone contacts: `apis.phone.search_contacts(access_token=phone_token, query='<identifier>', page_index=0, page_limit=20)` — paginating through all pages (read `references/pagination.md` for the loop pattern). Extract the matching contact's details programmatically in the SAME code block — never read the email from printed output and hardcode it in a subsequent block. Complete code pattern: `target = next(c for c in contacts if c['phone_number'] == '<identifier>')`; `target_email = target['email']`. Always pass `target_email` (the variable) in subsequent API calls (e.g., `receiver_email=target_email`) — never type the extracted email or name as a literal string copied from printout. App-specific user search APIs (e.g., `search_users`) search by name within that app's user base — they may return multiple irrelevant results when queried by phone number or email.
- When a task requires checking whether a person has an account on a platform (e.g., 'who do not have a venmo account'), do not treat search API results as proof of account existence — search APIs do fuzzy text matching and return partial matches. Instead, verify exact identity: after calling a search API, check whether any result's identifying field (email, username, phone_number) exactly matches the contact's corresponding field. If no result matches exactly, the person does NOT have an account on that platform. Example: `search_users(query=contact_email)` returns users whose names partially match the email string — only count someone as having an account if a result's email equals `contact_email` exactly.
- When a task references files or directories in the 'file system', use the `file_system` app APIs — never OS modules. Use `~/` for home directory paths (e.g., `~/photographs/`), not full paths derived from the email or username — the home directory name may not match the email prefix. Discovery workflow: (1) call `apis.file_system.show_directory(directory_path='~/<path>', access_token=token)` to list contents — keep `recursive=True` (the default) so that nested sub-directories are visible; setting `recursive=False` hides nested entries and risks missing target sub-directories, (2) filter the returned list for file paths matching the task criteria (e.g., electricity bills for this year, `.txt` files — `.pdf` files are not readable via show_file), (3) call `apis.file_system.show_file(file_path=..., access_token=token)` for each matching file. Never guess or hardcode file paths — derive them from the directory listing.
- When a task references a bill, receipt, or document by a time period (e.g., 'last month's internet bill', 'for March'), get the current date, compute the target period, and navigate the file system directory to find the file matching that period. File paths typically follow date-based naming conventions like /home/<user>/bills/<category>/YYYY-MM.txt. Extract amounts programmatically from file content using regex — never hardcode values seen in printed output.
- When a task involves splitting a cost equally, examine whether the actor (the user) is included in the split group. If the task says 'among X and me' or 'between my friends and me', the divisor is len(X) + 1 (including the user). If the task says 'among X' or 'between X' without mentioning the user, the divisor is len(X). Miscounting the divisor produces wrong amounts that fail tolerance checks.
- When an action requires selecting from multiple resources (payment cards, bank accounts, etc.) and the first attempt fails with a recoverable error (insufficient funds, expired card, etc.), filter out obviously invalid options first (e.g., expired cards: `valid = [c for c in cards if (c['expiry_year'], c['expiry_month']) >= (now.year, now.month)]`), then try ALL remaining resources systematically. Select a method programmatically — extract the ID from the stored variable, do not hardcode IDs from printed output. Trying options one by one by retyping the ID wastes steps on 422 errors. Do not call `complete_task(status="fail")` while viable options remain untried — at least one alternative often works.
- Obtain current date/time from `datetime.now()` or `apis.phone.get_current_date_and_time()`, never from internal knowledge. The latter returns `{'date': 'Thursday, May 18, 2023', 'time': '12:00 PM'}` — parse the date with `datetime.strptime(result['date'], '%A, %B %d, %Y')`, not with `'%Y-%m-%d'`. Always derive date components programmatically from the parsed result and USE them in filtering logic: `date_str = apis.phone.get_current_date_and_time()['date']; current_year = datetime.strptime(date_str, '%A, %B %d, %Y').year`. Never hardcode the year, month, or day in any context — not in assignments (`current_year = 2023`), not in comparisons (`year == 2023`), not in string filters. When a task says 'this year' or 'this month', use the programmatic variable in the comparison: `if year == current_year and month == 2:`. These values change across instances and hardcoding produces wrong answers.
- Only use provided app APIs and Python standard library (datetime, json, math, re, collections). No OS access.
- When verifying who has already completed an action (paid, sent, followed, etc.), read `references/action-verification.md` and follow its code pattern: write a code loop that iterates over fetched records and matches each expected actor by sender identity AND amount — never read printed output and match by eye. Eye-matching misses records when the list is long or amounts coincide. Keyword search also misses records, causing duplicate actions.

## Error Patterns to Avoid
- Passing an `answer` argument for action-only tasks — this causes answer mismatch failures even when the action was performed correctly. See Output Format.
- Using `page_limit` > 20 — AppWorld APIs reject values above 20 with a 422 validation error.
- Using wrong `sort_by` format — the `sort_by` parameter on list/search APIs must start with `+` (ascending) or `-` (descending), e.g., `sort_by="-created_at"`. Bare column names like `sort_by="created_at"` cause a 422 validation error.
- Forgetting to paginate — collection APIs return at most 20 results per page; missing pages means missing data. An un-paginated call returns a small default subset, not page 0 — when the task requires processing ALL items (e.g., 'reject all', 'delete all'), acting on this truncated subset causes complete task failure even though the action logic is correct.
- Manually fetching individual pages (e.g., separate calls for page_index=0, then page_index=1) instead of using a pagination while-loop — this requires reading printed output to decide when to stop and silently misses pages beyond the last manually fetched one. Always write a while-loop that automatically stops when `len(batch) < 20`; never hardcode page_index values or rely on printout to decide pagination extent.
- Hardcoding `page_index` inside a pagination loop — a loop like `while len(batch) == 20: batch = apis...(..., page_index=0, ...)` fetches page 0 forever instead of advancing pages. Always use an incrementing variable (`page += 1` after each iteration, `page_index=page` in the call) as shown in `references/pagination.md`.
- Computing `page_index` from the accumulated list length (e.g., `page_index=len(results)//20 + 1`) — this skips pages when the accumulated length crosses a boundary. After fetching page 0 (20 items), `len=20` gives `page_index=2`, skipping page 1 entirely. Always use a simple incrementing integer variable initialized to 0 and incremented by 1 after each iteration, never derive page_index from the list length.
- Calling `complete_task` before verifying the final state matches expectations.
- Abandoning a sound API strategy after a validation error — when the error message specifies valid values (e.g., 'Input should be X or Y'), retry with the corrected parameter. If the retry also fails, use `show_api_doc` to verify the parameter schema before switching to an alternative approach.
- Guessing API names, parameters, or response field names without checking `show_api_doc` first — response schemas often differ from expectations (e.g., `id` vs `song_id`, `name` vs `title`), causing KeyErrors and wasted iterations; parameter values also differ from expectations (e.g., `direction="outgoing"` when valid values are `"sent"`/`"received"`), causing 422 validation errors. Always call `show_api_doc` before the first call to any API, and use `show_api_descriptions` to discover all available endpoints. If a KeyError occurs on a response field, call `show_api_doc` to verify the correct field name before retrying — do not guess alternate names. If a 422 validation error occurs on a parameter value, call `show_api_doc` to find the valid values before retrying — do not guess. Do not use `.get(field, default)` to access response fields whose names you have not confirmed via `show_api_doc` — `.get()` with a default silently returns the default for a wrong field name, masking the error entirely. Use bracket access (`response['field']`) for unverified fields so a wrong name raises an immediate KeyError instead of corrupting results silently.
- Hardcoding entity IDs or other values from printed search/list API results into subsequent code — when a search API returns an entity with an ID field (artist_id, song_id, user_id, etc.), extract it programmatically from the stored response variable (e.g., `artist_id = next(a['artist_id'] for a in artists if a['name'] == 'Aria Sterling')`), never by reading the printed output and typing the literal value. Hardcoded literals break when results change across pages, runs, or data instances.
- Using app-specific social APIs (e.g., `venmo.search_friends`, `spotify.show_followers`) to resolve social relationship qualifiers ('friends', 'roommates', 'coworkers', 'family') — these return the app's platform connections (Venmo's social graph), not relationship-labeled contacts. The correct API is `phone.search_contacts(relationship='<type>')`, which returns contacts with explicit relationship labels matching the task qualifier. Using `search_friends` silently includes non-friends (platform connections without the relationship label) and excludes actual friends who aren't platform connections, producing wrong entity sets.
- Including parameters the API does not accept — after checking `show_api_doc`, verify each parameter in your implementation code appears in the doc's parameter list. Read/query APIs (e.g., `show_song_reviews`, `show_album_reviews`) may not accept `access_token` and use identity filters like `user_email` instead. Passing a parameter the API doesn't list causes an 'Unexpected parameter' error and wastes a step. Do not assume all APIs in an app share the same authentication parameter.
- Hardcoding amounts, dates, or other values from printed file/bill content into subsequent code — when `show_file` returns a bill or document, extract values programmatically using regex from the stored response variable (e.g., `total = float(re.search(r'Total Amount => \$(\d+)', bill['content']).group(1))`), never by reading the printed output and typing the literal number. Similarly, compute file paths programmatically from the current date (e.g., `path = f'~/bills/internet/{last_year}-{last_month:02d}.txt'`) and use `~/` not full paths — paths derived from printout hardcode the username and billing period, breaking across instances.

## Output Format
Call `apis.supervisor.complete_task(answer=..., status=...)` as the final step.

- **Question tasks** (the task asks "how many", "what", "which", "who", or otherwise requires reporting a value): pass `answer=<value>` where value is a minimal entity name or number, never a full sentence. Examples: "How many songs?" → `answer=5`; "Who sent the email?" → `answer="Alice"`.
- **Action tasks** (the task instructs you to DO something — follow, send, create, delete, add, remove, update, play, stop, clean up — without asking a question): omit the `answer` argument or set `answer=None`. These tasks are evaluated by checking database state, not the answer field. Examples: "Follow all artists" → no answer; "Clean up my library" → no answer.
- **Impossible tasks**: call `apis.supervisor.complete_task(status="fail")`.

Decision procedure: Does the task instruction ask for information (contains a question word or requests a value to report)? If YES → pass answer. If NO → omit answer.
