## Overview
Complete AppWorld tasks by calling app APIs through the pre-loaded `apis` object: log in with supervisor-provided credentials, resolve exact values before filtering, paginate every collection call, and verify every state change before calling `apis.supervisor.complete_task()`.

## Procedure
1. Load the task and credentials, then log in. Run `print(apis.supervisor.show_active_task())` for the exact query. Capture credentials once: `profile = apis.supervisor.show_profile()` and `creds = apis.supervisor.show_account_passwords()`; build `pw = {a['account_name']: a['password'] for a in creds}`. Gate: `assert any(a['account_name'] == '<target app>' for a in creds)`. Call the login API of every app the task spans whose later calls need an `access_token` — the primary app named in the task AND each auxiliary app a later rule reads from (the contacts app that owns relationship data when resolving people groups; the environment clock API takes no token, so it needs no login) — each with the account identifier `profile` exposes for that app (email or phone number) and `pw['<that app>']`, referencing the captured variables verbatim, and store each returned `access_token` in its own variable. Never hardcode or retype a username/password from memory.
2. Load the pagination and inspection helpers immediately after logging in, as the very next code block — before any collection call, including a first "inspect the data" call. `SKILL_DIR` is not pre-defined in the REPL: define it in the same block first — `from pathlib import Path; SKILL_DIR = Path('<skill dir shown in the Skill Resources section of the system prompt>')` — then run both helper loads in the same block: `exec((SKILL_DIR / 'scripts/pagination.py').read_text())` and `exec((SKILL_DIR / 'scripts/inspect.py').read_text())`. Registering `preview`/`select_records` here, before any collection is fetched or printed, means no fetched set is ever inspected with a manual for-loop. A paginated endpoint called before this step returns only the first page and silently hides records, so never call one directly.
3. Resolve referential phrases before selecting data: when the task says "as per their request", "reply to them", or points at a prior message/document, read that message or document first and extract the exact request criterion (who asked and what they filtered on). Guessing the criterion silently selects the wrong subset. When the task points at a file-system document, locate it with a scoped listing (`show_directory(directory_path='/home/<username>/<folder>', recursive=True)` or `show_directory(substring='<term>', recursive=True)`) and only then read the matched file; never call `show_directory(directory_path='/', recursive=True)` to discover a document — a whole-tree dump floods context like a large collection dump. Before opening a month-keyed bill/receipt file ("last month's bill"), run the month-derivation gate required by the Rules: compute the target `YYYY-MM` prefix from the queried current date in code, then `assert` the chosen file's name starts with that prefix (or that its date field matches) and print the candidate month-prefixed files to confirm the pick. Never hardcode a `YYYY-MM.txt` path — a wrong-month file silently changes the amount and fails the share assertion.
4. Confirm every category/enum filter value before filtering: print the app's enumeration API and check the filter string appears verbatim. The DB comparison is exact, case-sensitive string matching, so a guessed label silently selects the wrong subset.
5. Translate quantity phrases into inclusive filter bounds before calling a search/list API: `at least N` / `minimum of N` -> `min_*=N`; `more than N` -> `min_*=N+1`; `at most N` -> `max_*=N`; `fewer than N` -> `max_*=N-1`.
6. Fetch every paginated result through `get_all_pages(...)`: the target app's main collection AND any auxiliary lookup (e.g. a contact/relationship search) used to build a filter set. The inspection helpers `preview`/`select_records` were loaded in step 2. Gate: for every fetched set run `assert isinstance(c, list)` then `preview(c)` (prints the total count plus at most the first 3 records) before filtering on it. `preview(c)` returns the full list unchanged — only its print is capped — so records beyond the preview are still in the variable. To view a specific stored record, index it (`print(c[3])`), and never re-fetch a collection you already stored. Never print a whole stored collection with `preview(c, n=len(c))` or an indexing loop: a full dump of a large list (e.g. a sent-request or transaction history) floods the context just like a manual for-loop and triggers a repetition loop over initialization steps. Filter in memory with `select_records(c, lambda r: <condition>)`, which prints only the match count plus a small sample. Never inspect a fetched set with a manual `for r in c: print(r)` loop: a verbatim dump of even a few dozen records (e.g. a sent-request or transaction history) floods the context and triggers a repetition loop over initialization steps instead of mutating. After any query-filtered call, gate that the query actually filtered: `assert len(filtered) < len(unfiltered)` (or assert the query token appears in the returned records); when the assert fails because the count equals the unfiltered fetch, drop the `query`, re-filter the full stored list with `select_records(c, lambda r: <condition>)` and confirm the match count — never treat a query ignored by the endpoint or a positional first hit as the subset. After applying any `min_*`/`max_*` bound, cross-check the filter before mutating: re-fetch the same collection without the numeric bounds and `assert` the filtered IDs equal the IDs in the unfiltered list that satisfy the bound.
7. Compute the plan in memory before any mutation. Combine conditions literally: `or` -> set union (`|`); `and`/`all` -> `all(...)` or set intersection — this mapping applies to filter criteria on records, while named collections joined by "across ... and ..." are a UNION (see the unique-count rule). When the task scopes a mutation to records matching criteria spread across TWO collections (e.g. "songs in my album library which I have liked"), fetch both collections, map each to its ID set, and compute the target set in code by the qualifier's polarity: a positive qualifier ("which I have liked") is the INTERSECTION of the two ID sets; a negated qualifier ("which I have not liked") is the set DIFFERENCE (`A - B`), because the second collection may include records the base collection does not (e.g. liked songs outside the library) and only the difference keeps them out. Treating a negated qualifier as an intersection, or mutating the whole base collection instead of the difference, selects the wrong subset and fails the exact-ID side-effect assertion. Derive every identifier in code from the stored results — mutation targets, the records you read, and the objects you verify: select notes/contacts via `select_records` on a stored list, reuse a create/send API's returned id (`result['<id field>']`) for the follow-up show/verify call, and never retype an id you saw in printed output, because a transcription error silently moves or re-reads the wrong record. When a descriptor must resolve to exactly one record, gate before indexing: `assert len(matches) == 1`. When the plan scopes a filter by a relative-time phrase, derive the year/month boundaries in code from the queried current date and never type a 4-digit year literal into a predicate. For a plain `this year` / `released in this year` filter, compute the subset once with the `filter_by_year` helper and make ITS output the sole target of downstream operations — for a phrase combined with a second criterion such as a genre, fold that criterion into the helper argument: `filtered = filter_by_year(records, '<date field>', apis.phone.get_current_date_and_time, predicate=lambda r: r['<other field>'] == '<value>')`. Then re-run the helper on the full list and assert the id sets match: `derived = filter_by_year(records, '<date field>', apis.phone.get_current_date_and_time); assert set(r['<id field>'] for r in filtered) == set(r['<id field>'] for r in derived)` — and mutate/verify using `filtered` (the helper's return), passing the same `predicate` so both calls choose on identical criteria. Never build the subset with a hardcoded year first (e.g. `this_year = 2023; [r for r in records if r['<date field>'].startswith('2023')]`) and then use a later cross-check as a recovery: when the clock year coincidentally matches the literal the wrong-by-construction list silently survives as the mutation target, so the gate never fires and the failure mode is exactly what it was meant to eliminate. For a named month of this year plus a residual others bucket, derive `this_year = current_year(apis.phone.get_current_date_and_time)` (loaded from `scripts/relative_dates.py` per the References entry) and reference `this_year` in every bucket predicate — never type a 4-digit year literal. Gate: `assert not (set(to_keep) & set(to_remove))`; for a named-month-plus-others partition also `assert (set(named) | set(others)) == set(all_ids)`, `assert not (set(named) & set(others))`, and `assert all(datetime.datetime.fromisoformat(r['<date field>']).year == this_year for r in named)` — the last gate fails the moment any named record falls outside the clock-derived year, so a hardcoded year diverging from the simulated this year aborts before any mutation.
8. Derive the mutation split from the stored target ids and the already-fetched per-id existing state before mutating: `to_create = sorted(set(target_ids) - set(existing_records))`, `to_update = [i for i in target_ids if i in existing_records and existing_records[i]['<value_field>'] <op> <target>]`, `to_skip = sorted(set(target_ids) - set(to_create) - set(to_update))`. Gate: `assert sorted(set(to_create) | set(to_update) | set(to_skip)) == sorted(set(target_ids))` — this aborts the moment an id is retyped from printed output or dropped, instead of silently mutating the wrong record. Apply the mutation in that order (create records that have none, update records whose value is on the wrong side of the target, skip records already at or beyond it per the create/update/skip Rules). Build the affected-id set once in code from the stored target subset — `affected_ids = [r['<id_field>'] for r in <stored target subset>]` — and drive the mutation loop from that list (`for id_ in affected_ids: ...`), never from a literal id list retyped from printed output. Then verify with the printed output capped to the affected records: re-read the collection and `select_records` onto the IDs just created/updated — `verify = select_records(c, lambda r: r['<id_field>'] in affected_ids); assert set(r['<id_field>'] for r in verify) == set(affected_ids)` — and assert the intended scalar state on every affected record with a real assert — `assert all(r['<value_field>'] == <target> for r in verify)` (and, for removals, `assert all(r['<id_field>'] not in <remaining_ids> for r in verify)`) — never a printed boolean, which would still reach complete_task() even when a check fails. The assert must compare against `affected_ids` derived from the stored subset (or the helper's return), never against a retyped literal set such as `assert set(post_ids) == {265, 273}`: a literal set repeats whatever the mutation loop used, so the check passes even when the mutation used the wrong subset — only a comparison against the code-derived target set catches divergence. Never `preview(c, n=len(c))` or dump the whole collection to verify a mutation: the full history floods the context and restarts the initialization loop instead of reaching step 9. Fix and re-verify before continuing, then call `apis.supervisor.complete_task()` in the next code block.
9. Finish with `apis.supervisor.complete_task()`; pass `answer=` only when the task asks a question, and keep it a bare entity name or number.

## Rules
- Look up credentials and personal info only via supervisor APIs; never guess account names or passwords.
- Resolve category/enum filter values before filtering; the DB comparison is exact and case-sensitive. Prefer the app's enumeration API when one exists. Many list/search filter tokens (a direction/status token, for example) have no enumeration API; resolve those from the parameter's own doc: check `apis.api_docs.show_api_doc(app_name=..., api_name=...)` for a `constraints` entry on that parameter (e.g. `value in ['sent', 'received']`) and copy one listed token verbatim. When no constraints entry exists, send the read-only call once with the most literal token: if it 422s, the error message lists the accepted values verbatim, so re-send with one of those exact tokens — never a second guessed synonym; if it silently returns rows instead of rejecting, drop the token and compute the predicate in code over the unfiltered list per the lifecycle-state rule rather than trusting the guessed subset.
- Determine a record's lifecycle state from the record's own state fields, not a guessed status filter token: a request is "pending" when its resolved/acted-on timestamps are unset (`approved_at is None and denied_at is None`), a message per its read/seen field, a task per its completed field. Compute the predicate in code over the fetched list, and pass a status filter only after the rows confirm its tokens — a guessed token silently returns the wrong subset and no enumeration API may exist.
- Filter bounds are inclusive: `at least N` includes records exactly at N, so a strict reading drops boundary records and fails the task.
- Pagination is decided by the API doc, not the API's name: fetch every endpoint whose docs list `page_index`/`page_limit` through `get_all_pages(...)`, including `show_*` collection endpoints and auxiliary contact/relationship searches used to build a filter set. Never call such an endpoint directly or pass a guessed `page_limit`, because an unpaginated call silently returns only the first page (often the oldest records) with no error. Call `get_all_pages` with the API function object itself — `get_all_pages(apis.<app>.<list_api>, access_token=token)` — never `apis.<app>` plus a string API name, which raises `TypeError: ... object is not callable`.
- Verify a search actually filtered before relying on its result: a free-text `query` argument may be ignored entirely (a `search_*` call with `query='<token>'` can return the same count as the unfiltered call). Run the query-filter gate from Procedure step 6 before treating any query-filtered call as a subset, and never take an accidental first hit by position inside an unfiltered result as the match.
- When a task refers to a specific record by a descriptor, resolve it with the `resolve_one` helper loaded in step 2: pass the fetched full list (no free-text `query` for a simple name match, since search endpoints may ignore the query) and a predicate matching the label/name/title field, preferring an exact case-insensitive match normalized for punctuation (a "go-to-sleep" alarm matches the label "Go to sleep"), then falling back to the closest semantic match. `resolve_one` prints the matched candidates, asserts exactly one best match, and returns the record — take the record's id and every identifier (email/phone/username) from that returned dict instead of guessing by time, position, or order and instead of re-typing values seen in printed output.
- Resolve people-group references (`coworkers`, `friends`, `family`, `roommates`) via the app that owns contact/relationship data: list the available relationships, then run one paginated contact search per named relationship and union the emails/names (`a | b`) — a task naming several groups spans their union; "and" joins groups, it does not mean members of every named group. Match target-app records against that union, never assuming identity from the group label alone or searching only the first named group. The target app's own in-app friend/contact list is NOT this group (it can include outsiders and omit members): resolve membership only from the contacts app's relationship enum and never union the target app's friend list into the set — one extra or missing member fails the exact-ID side-effect assertion.
- When a task mutates the child items owned by entities the user follows or subscribes to inside the target app ('like all the songs from the artists I follow'), resolve the relationship from that app's own following/subscription list, not from a people-group or contacts lookup: fetch it with get_all_pages (e.g. show_following_artists) and enumerate every followed entity's children through the app's per-entity search/list API (get_all_pages with the entity id, e.g. search_songs(artist_id=...)). Collect every child id into the target set and dedupe by id, because a child owned by two followed entities is returned once per entity and would otherwise be mutated twice. This is the one case where the target app's own in-app membership list is the authority: the people-group rule's ban on the target app's in-app friend list applies only to named person groups (coworkers/friends/family/roommates), not to the app's own follow/subscribe relationship.
- When the task asks which members of a resolved candidate set do or do not have an account on another app ('my siblings and roommates, who do not have a venmo account'), load `scripts/account_check.py` per its References entry instead of improvising a per-candidate free-text search; it returns an `{email: has_account}` map and prints only one boolean per candidate. Send/mutate only the members on the required side of that boolean — the members whose email is NOT in the map for 'who do not have', or whose email IS in it for 'who do have' — passing each member's own identifier from the stored contact record (e.g. its `phone_number` to the send-message API).
- When a task targets a person or record by a raw identifier (a phone number or email) rather than a named group or descriptor, resolve it through the app that owns that identifier. A phone-number search endpoint may not accept the identifier as a filter parameter (e.g. `phone.search_contacts` allows only `access_token`, `query`, `relationship`, `page_index`, `page_limit`), so passing it as a kwarg raises an "Unexpected parameter" error and is never the fix. Read the endpoint's allowed parameters from its `show_api_doc` or the validation error, fetch the full collection through `get_all_pages(...)` — never a direct call that returns only the first page and can silently miss the match — then resolve it with the `resolve_one` helper loaded in step 2 — `match = resolve_one(c, lambda r: r['<field>'] == '<value>')` — which prints the candidates and `assert`s exactly one match. Assign the target-app identifier from the returned dict (`receiver_email = match['email']`) and pass that variable into the follow-up call, never as a hardcoded literal retyped from printed output — a transcription slip sends the money to the wrong account and fails the exact-receiver assertion. Never pass the raw phone number to an API that requires an email/username and never take a positional first hit inside an unfiltered result.
- Convert relative-time phrases into concrete dates by deriving them from the environment's current date/time in code — query `apis.phone.get_current_date_and_time()`, since the sandbox wall clock may not match the task's simulated "today"; a hardcoded or copied date literal silently selects the wrong records when the simulated date differs. Phrases include `yesterday`, `today`, `last week`, `last month`, `last year`, `this year`, `this month`, and `<Month> of this year`. For `today`/`yesterday`, load `scripts/relative_dates.py` per the References entry and call `today, yesterday = today_and_yesterday(apis.phone.get_current_date_and_time)`, then pass the returned ISO day strings into the filter — never hand-write a literal ISO date (e.g. `'2023-05-19'`) in a filter argument. For `this year` / `released in this year`, load the same script and call `matches = filter_by_year(records, '<date field>', apis.phone.get_current_date_and_time)`, which derives the current year from the environment clock and returns the records whose date field starts with that year — never write a 4-digit year literal into a predicate, because the simulated year can differ and a hardcoded year silently selects the wrong records. For month-level phrases, derive the month from the environment clock in code: for `this month` / `last month` load `scripts/relative_dates.py` per the References entry and call `start, end = month_bounds(apis.phone.get_current_date_and_time)` (`months_ago=1` for `last month`), then pass `start`/`end` as the API's inclusive date filters or match the derived `start[:7]` `YYYY-MM` prefix in memory; for a named month of this year (`March of this year`) derive `this_year = current_year(apis.phone.get_current_date_and_time)` and match the `f'{this_year}-{month:02d}'` prefix. Never use the month alone or a hardcoded 4-digit year/month literal: same-month records from a different year leak into the named bucket, and a hardcoded year silently matches the wrong records (or an empty window) whenever the simulated date differs. When a month phrase points at a bill/document file, select the file whose name or date field matches the derived month and print the candidate months to confirm you pick the right one (e.g. the prior month, not the current one) before reading it. Duration-of-state phrases ('for N or more days', 'for at least N days', 'has not been approved/denied for N days') bound the record's creation timestamp N days before the queried now with an inclusive `<=`: `record[<created_field>] <= now - datetime.timedelta(days=N)` ('more than N days' uses strict `<`; 'fewer than N days' uses `>`), combined with the state predicate over the record's own fields, never a guessed status token. When several records match the query text and the task pins a relative time, pick the record whose timestamp is closest to that reference and print each candidate's timestamp to confirm.
- When a task shifts a stored time earlier or later by a duration ("move ... to 1 hour later", "N minutes earlier"), compute the new time in code from the record's current time, handling hour/minute carry and midnight rollover. AppWorld patches `datetime.datetime` to a frozen-time `FakeDatetime` that has no `timedelta` class attribute, so `from datetime import datetime` makes `datetime.timedelta(...)` raise AttributeError; use module form `import datetime` and call `datetime.datetime.strptime(s, '%H:%M')` plus `datetime.timedelta(minutes=N)`. Write back in the same 24-hour zero-padded HH:MM format. Identify the record to mutate with the descriptor-matching rule, store it in a variable, and take the record's own id and time fields from that stored variable for both the computation and the update call; never re-type the id or time as hardcoded literals copied from a printed list, because a transcription or selection error silently moves the wrong record.
- For "newest / oldest / latest / most recent" questions, aggregate the full candidate set from every collection the query names at the granularity of the object the question names (a "song" question aggregates songs), dedupe by ID: when a named collection is a container whose entries hold member IDs (e.g. an album/playlist library entry's `song_ids`), descend into the member IDs and treat each member as a candidate — a container's own date field (an album's `release_date`, a playlist's `created_at`) is the container's date, not its members', and never serves as a proxy for the members. Fetch each item's timestamp/date field via its detail API (the field matching the concept — e.g. released -> release_date, not a generic added_at/created_at), and pick the record with `oldest_by_field(records, '<date field>')` (oldest) or `newest_by_field(records, '<date field>')` (newest/latest) - load `scripts/dates.py` per the References entry first. The helpers parse each value with `datetime.fromisoformat` before comparing, so a mixed date format cannot silently mis-order records. Never compare raw date strings with `<`/`>`/`sorted`, and never look at only one collection. Apply the same timestamp selection when an action (not a question) targets "the last / latest / most recent" record within a person-specific subset (e.g. "the last request I sent to X"): fetch the full collection, filter to that person, then select it with `newest_by_field(filtered, 'created_at')` (which parses the timestamps before comparing), print each candidate's timestamp, and confirm it matches any stated status qualifier (e.g. "they approved it" -> its `approved_at` is set). Never trust the API's implicit list ordering.
- For "most / least <metric>" selections ("most listened to / played", "most / least liked", "highest / lowest rated", "most followed"), the superlative names a numeric detail field, not a date or a position: when the metric is scoped to a named artist/performer/entity ("the least played song by X"), first resolve that name with `resolve_one` over the full, query-free collection fetch (never a free-text `query`, which search endpoints may silently ignore and return the whole catalog) and take the entity id from the returned dict, then fetch the named collection(s) — never retyping the id from printed output — descend into container member IDs per the newest/oldest rule, read each member's metric from its per-item `show_*` detail API, and pick the `max`/`min` member — map the phrase to the field the API names (listened/played -> the play-count field, liked -> the like-count field, rated -> the rating field, followed -> the follower-count field). Never proxy a container's own aggregate for its members and never take the first member by position.
- For "longest / shortest / total / average" aggregate questions over a numeric member attribute of a container (e.g. "how long is my longest playlist"), compute a per-container aggregate in code: a container's value is the SUM of its members' values for that attribute, so "longest" takes `max` and "shortest" takes `min` over the per-container sums — never a member-level max and never the newest/oldest timestamp rule. Fetch every container through `get_all_pages` (the library list exposes only member IDs), sum each container's members via the per-item detail API (see the list-omits-fields rule; the per-container detail API returns the members with the attribute and serves as an independent re-check), then take `max`/`min` over the per-container totals for longest/shortest, or `sum`/`mean` across containers for a total/average. Convert the source unit to the question's unit in code — infer the source unit from the value magnitude when the doc omits it (e.g. a song duration in the hundreds is seconds) — round to the nearest integer with `round(x)`, and pass the bare number to `complete_task`.
- For questions that count or list unique items across several named collections ("how many unique X are there across my library A, my library B and all containers C?"), fetch every named collection through `get_all_pages`, map each entry to the item ids it owns — a flat library entry contributes its own id field, while a container entry (album/playlist/folder) contributes its embedded child-id list — then answer `len(set(all collected ids))`. "across ... and ..." joining named collections is a UNION of those collections with dedupe by id, never an intersection: intersecting answers a different question (items present in every named collection) and collapses toward zero. "and" means set intersection only when it conjoins filter criteria within records (e.g. "items in a container collection which I have liked").
- List/search endpoints often omit detail fields that their per-item `show_*` endpoint returns (a list entry may carry only item IDs, or lack a per-item detail such as a release date, and a feed entry may lack a per-item flag such as `liked`); when the task needs such a field, union the item IDs from every relevant collection and call the per-item `show_*` API for each ID. Never guess or filter on a field the list response lacks, and never read a possibly-absent field via `record.get(key, default)`: a missing key silently yields the default, so a pre-state or post-mutation check against list/feed entries reports the default instead of the real value — read such fields from the per-item `show_*` response.
- For a like/follow/add mutation driven by a boolean state flag, the per-record private/detail API is the canonical source of that flag, never a dedicated 'list of things I X'ed' collection (show_liked_songs, show_liked_albums), which can omit records that are already X (e.g. a liked song that is not in the song library), so subtracting that collection's members from the target ids wrongly re-targets already-X records and causes redundant mutation calls that fail with 422 'already X'. Read every target's flag from its per-record private/detail API (show_*_privates, or the per-item show_* detail) for BOTH the pre-state (skip targets already at the target value and confirm the skip set) and the post-state, and gate the post-state per the verify-write rule. If a like/follow call still returns an 'already X' 422, treat that target as already-at-target and move on; never wrap the mutation loop in a blanket try/except Exception, because only the 'already X' condition is benign and any other exception must abort the block before complete_task.
- Compute keep/remove decisions in memory before mutating; never mutate a collection while iterating over it.
- Scope "the rest"/"others"/"all other" as the set complement of the explicitly named or matched set, computed in code — never guess a residual predicate such as a date range or month observed in the data. For updates, complement means records not already in the target state (to "disable the rest", disable only the enabled records other than the target, leaving already-disabled ones untouched), so a no-op update is not recorded as a spurious change. For partitioning a collection into named buckets plus a residual "others" bucket, assign the residual every record matching none of the named buckets and assert every record landed in exactly one bucket, with no unassigned record remaining.
- When updating a record, pass only the identifier plus the field(s) the task actually changes, and omit every unchanged field: update APIs apply every key you pass and leave omitted optional fields as-is, so echoing unchanged fields can overwrite them and fail assertions that only the intended field changed.
- For reimbursement/split-cost tasks, load `scripts/reimbursement.py` per the References entry and build the owed mapping entirely from helper results: `shares = parse_shares(note['content'])`; `paid = received_payments(transactions, '<description>', <own email>)` — select incoming payments by the SAME description string used on the outgoing requests plus your own receiver identity, never by a created_at/time window, since a phrase like 'already sent me their share' supplies no cutoff and a guessed date silently drops an early same-event payment — then create requests/charges only for the entries whose payer is not in `paid`. When several notes share the event name, choose the note whose paid entries are consistent with the received payments: the already-paid payers and their EXACT amounts must appear verbatim in that note; `assert` each received payment's amount equals the chosen note's entry for its payer, then request only the chosen note's entries that have no matching received payment. Derive each recipient's identifier with `resolve_emails(contacts, [n for n in shares if n not in paid])` — it asserts exactly one contact match per name — instead of retyping emails or taking the first search result by position. For a total "shared equally" among a group of others plus yourself ("among <group> and me", "including me", "between us"), compute each share as `round(total / (len(group) + 1), 2)` — the divisor is the group size PLUS one for yourself; dividing by `len(group)` alone overcharges every other party.
- Payment direction maps to different APIs and reverses who moves the money: sending money TO someone ("pay X", "send X the money back", "reimburse/refund X") uses the app's send/pay API with the payee's identifier and the owed amount; asking money FROM someone ("request X $", "charge X", "ask X to pay") uses the app's request/charge API with the counterparty as the requester. Read each candidate API's description and match its direction to the task before choosing; the opposite-direction API creates the wrong record type and fails the test.
- When a send/pay API call fails with an insufficient-balance error (e.g. "Your Venmo balance does not have $68.00 to make this transaction." / "does not have $100.00"), do NOT pre-fund the balance with the app's add-to-balance/top-up API and retry: the top-up writes an extra balance-transfer record plus receipt file/directory side effects that the grader's exact-model-changes check rejects as unwanted side effects, failing the task even though the eventual payment is correct. Fund the payment in the SAME call by reading the send/pay API's full parameter doc (`apis.api_docs.show_api_doc(...)`) and passing its optional funding-source parameter (e.g. `create_transaction(..., payment_card_id=<id>)`), so only the expected transaction and notification records change. Pick that card in code with the clock-derived payment-card helper instead of hand-written expiry logic: load `scripts/payment_cards.py` per its References entry, fetch the card list (`cards = apis.<app>.show_payment_cards(access_token=<token>)`), and call `today, valid = valid_payment_cards(cards, apis.phone.get_current_date_and_time)` — it derives the simulated "today" from the environment clock, keeps only the cards whose `expiry_year`/`expiry_month` are not already past it (a card expiring in the current month is still valid), and prints the surviving card ids. Never type the simulated date or the expiry threshold as a literal: a hardcoded year/month silently keeps an expired card or drops a still-valid one whenever the simulated date differs. Then pass the remaining cards in turn until one is accepted, printing each card id and the failure reason (an expired card raises its own error; a card with too little funds errors with "does not have $N") — a failed send call writes no record and is safe to retry, whereas a successful pre-fund writes a balance-transfer record permanently. Never hardcode or guess a card id, and after the funded payment assert no extra models were created (e.g. the balance-transfer history is unchanged) before `complete_task`.
- Map privacy/visibility modifiers onto the API's privacy flag explicitly when a task states one: "privately"/"private" -> `private=True`; "publicly"/"public" -> `private=False`. Never leave the flag unset assuming a public default — the create API and its `show_*` response default to `private=true`, so an omitted or inverted flag leaves the post private and fails the public/private assertion even when the amount and recipient are right.
- When a task quotes a literal string to attach to a mutation — a description/note (e.g. "For electricity bill."), a message body, an email subject, or a label — pass that string verbatim (exact words and punctuation, nothing added or dropped) into the API call. Graders compare the written note/message against the expected text after light normalization, so a paraphrased or embellished string fails the match even when the amounts and recipients are correct.
- To accept/decline inbound payment or reimbursement requests ("accept/approve"/"decline/deny" the pending requests from some people), list the requests you RECEIVED via `get_all_pages` (the received-requests endpoint, per the payment-request endpoint-distinction rule below), match each request's sender against the resolved people-group emails, and call the approve/deny API once per matched id. Act only on still-pending requests and leave non-group senders untouched — re-resolving a resolved request or approving an unrelated one is an extra side effect that fails the test.
- Distinguish payment-request list endpoints by who owns the request: tasks acting on requests YOU sent ('my payment requests to X', 'remind/cancel my requests') read the sent-requests endpoint and match each record's `receiver` against the resolved group; tasks acting on requests you RECEIVED ('requests from X', 'requests to me') read the received-requests endpoint and match each record's `sender`. Picking the wrong endpoint silently selects the other half of the ledger. To send a reminder, call the app's remind-request API once per qualifying id: it takes only the id and auto-generates the message (never pass a `message` argument). The reminder is delivered as a notification to the receiver and leaves the request pending (`approved_at`/`denied_at` unchanged), so re-reading the request cannot confirm delivery; instead assert every reminder call returned a success response and that the success count equals the qualifying id count.
- When extracting a filtered subset from a note or document's free text (records written as a title line plus indented `- key: value` sub-lines), load `scripts/keyed_entries.py` per its References entry and select the matching entries in code - match the resolved request criterion against the sub-line values (e.g. `- director: X`) and never read the printed content and retype the matching values by eye, since a transcription slip or a subtler criterion silently adds or drops values. Include every matching entry, exclude every non-matching one, and scan all source collections so a match hidden in a second document is not missed.
- When replying to a text or email thread, act on the inbound message that matches the active task's topic (the one naming the task's object) and ignore earlier, already-answered requests on other topics.
- When the task says to send the owed money as per a text/email conversation and the thread quotes several dollar figures, select the amount from the turn that discusses the object named by the task's note/description (e.g. the grocery turn for a note saying "Thanks for the groceries!"), and ignore figures tied to a different object or explicitly settled by a later turn ("call it even", "already paid", "it's on me"). Extract the chosen figure in code from the stored message text (re.search(r'\$(\d+(?:\.\d+)?)', msg)) instead of re-typing it from the printed transcript, print the chosen turn with its surrounding messages to confirm the object matches, and pay exactly that amount.
- For read-only questions ("what is...", "how many...", "total cost...", "list..."), never create, copy, move, update, or delete any file, directory, or record — including copy_file/move_file used to inspect content. Inspect only via read/show/list APIs: any file the task did not ask you to change is a side effect that fails the "no model changes" check even when the numeric answer is correct.
- When a task sums a value across bill/document files, select files by the resolved category and time prefix, take each file's total from its labeled line (match the label, e.g. `Total Amount => $N`) — never the last dollar sign in the text, which silently picks a different field if the format changes — and sum only those values. `show_file` returns non-text files (PDFs/images) with `content` beginning `binary:`; that string is undecodable (hex/base64) and a `.txt` copy does not recover it, so skip those files and read a text twin when one exists. Print the contributing files and assert the set matches the resolved filter before answering.
- For "how much did X pay/receive" sums over payment transactions, select the contributing rows by every constraint the task names: counterparty AND time AND the named event/merchant matched case-insensitively as a substring of each row's description (wording varies — "Food at <place>", "Lunch at <place>", or the bare place name — so leaving the description out silently adds unrelated payments). Print each contributing row's description and confirm it matches before summing. When the task also states a known own portion excluded from the queried set ("except mine", "my share was $N", "including me"), add it in code: `total = sum(matched rows) + stated_own_share`, never search the visible set for it.
- For conditional state-setting tasks ("give a rating/value of X to each record in a subset", "increase to X if lower", "decrease to X if higher"), fetch each target's current value first, then split in code by the qualifier's direction: already at X -> skip (a no-op update is a spurious change); on the change side (value < X for "increase", value > X for "decrease") with an existing record -> update with only the identifier plus the changed field; already on the no-change side -> skip; no existing record -> call the matching create API — never call create over an existing record (it duplicates) or update over a missing one (it fails). For per-user state (ratings/reviews), read the user's OWN record via the per-item `show_*_reviews` API scoped to the user's identifier through `get_all_pages`, never the item's aggregate `rating`/`rating_avg` field, which blends other users' ratings.
- The file_system app resolves paths against `/` and does not expand `~`: translate a query path `~/X` into the absolute `/home/<username>/X` (derive `<username>` from the supervisor profile's lowercase first name, or list `/home/` once). A relative path like `photographs/vacations` resolves to `/photographs/vacations/` and is reported unavailable when the account's files live under `/home/<username>/`, and an empty path fails validation.
- For file/directory organization tasks (moving or filing files into folders), list the target directory and, when the listing returns only paths, fetch each entry's per-file detail API to obtain the field the task keys on (e.g. creation date lives on the file detail record). Classify every file by the resolved criterion, create the destination directories first (idempotently) before moving, move each file into a destination path built from the original basename so file names and contents survive, then verify the placement in code before `complete_task`: re-list each destination directory and `assert` its file set equals the basenames the plan moved there, and re-list the source directory and `assert` it now contains only the destination subdirectories (no file remains at the source). Printing the listings is not verification — a run that only prints '<source> (should be empty of files)' and proceeds without an assert has not checked placement. Never delete-and-recreate a file to move it.
- Verify every write by re-reading the record after the mutation and asserting the change took effect before completing. Re-read the changed field from an endpoint whose response actually contains it — the per-item `show_*` detail API when the list/feed response omits the field — not from the list entry. When only a filtered subset must change, snapshot the excluded records' pre-mutation state in code BEFORE mutating (e.g. the ids and values of records you already own, such as your existing review ids and their ratings), then after mutating re-read them and `assert` the post-mutation state equals that snapshot. A record already present in the pre-snapshot is not a change and must not be flagged; a record that appears only after mutating (or whose value changed) is an over-broad mutation and the `assert` must abort before `complete_task`. Use a real `assert`, not a printed boolean that proceeds to `complete_task` when it prints False.
- After computing an aggregate answer, re-derive it with an independent check before calling `complete_task`. For oldest/newest/top-k/min/max over a detail field, sort the full list by that field and print the top few. For a unique-count/union answer over several collections, recompute the union a second way — e.g. inclusion-exclusion from the per-source sizes and the printed pairwise/triple overlaps, or rebuild the set through a different code path — and confirm both results agree.
- The sandbox blocks `csv.writer` (calling it raises "Usage of the following function is not allowed: csv.writer"); when a task requires exporting a CSV or TSV file, build the content manually: write the header row then one line per record, escape each embedded `"` as `""`, and wrap in double quotes any field containing a comma, quote, or newline.
- When a task exports or backs up data and then terminates/deletes the account, do every read and the export first, re-read the written file to confirm it landed, and only then delete the account: account deletion invalidates the access token, so any API call after it fails with 401 and the not-yet-exported data becomes unreachable.
- Code blocks must contain only valid Python. Close with the standard fence and nothing else — an XML/HTML-style closing tag after the code is executed as Python and aborts the block with a Syntax error.

## Error Patterns to Avoid
- Calling a paginated collection endpoint directly instead of through `get_all_pages` — including auxiliary contact/relationship lookups used to build a filter set — and trusting a truncated first page as the complete set.
- Treating `at least N` / `minimum of N` as strict inequality, which drops boundary records such as exactly 22 followers.
- Guessing a category/enum label instead of resolving it from the enumeration API, silently selecting the wrong subset.
- Re-submitting identical code after an execution error: read the traceback, locate the offending line, and fix or delete it. If the same error persists after 2 attempts, rewrite the block from scratch.
- Re-running initialization steps (`show_active_task`, login, loading the pagination helper, `get_all_pages`) in a loop after they have already succeeded: once a lookup returns a complete result, store it in a variable and advance to the next Procedure step. Never repeat a block whose output you already captured, even when a previous block printed a very large result.
- Writing state (follow/like/add/remove) without checking the pre-state and re-checking the post-state, leaving wrong IDs or silent no-ops undetected.
- Calling `complete_task` without re-querying the final state, passing full sentences as answers, or passing `answer` for action-only tasks.

## Output Format
Call `apis.supervisor.complete_task()` as the final step. Omit `answer` for action-only tasks. When an answer is required, return only the bare entity name or number, not a sentence. For numeric answers pass the bare number with no currency symbol, thousands separator, or unit (`answer=368`, never `answer="$368"` or `answer="368 dollars"`): AppWorld graders normalize answers with `float()`, which rejects `$`, `,`, and unit words, so a formatted value fails the `assert answers match` check even when the computed number is correct. When the task is to send or reply with a comma-separated list, send the bare joined string: build the list and send `', '.join(items)` with no extra entities, commentary, or Python list syntax — graders substring-check the sent message against expected and excluded tokens.
