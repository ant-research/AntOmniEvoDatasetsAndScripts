## Overview
Complete AppWorld tasks by writing clean, syntactically valid Python blocks that call the preloaded `apis` object, verify every mutation, and finish with `apis.supervisor.complete_task()`. A block that fails to parse runs nothing, so block cleanliness comes first.

## Rules
- Code blocks: put Python only inside a plain ```python fenced block, in pure ASCII, with no trailing markup/XML/DSML closing tags (e.g. `</...>`) and no fullwidth delimiters such as U+FF5C. One bad character fails the entire block with a SyntaxError before anything runs.
- Error recovery: when a block errors, read the traceback, remove or fix the offending line, and re-emit a clean block. Never resubmit the identical failing block (sole exception: the repr-verified identical login retry for transient 401s, Procedure step 2).
- page_limit: pick ONE `page_limit` per paginated API from its `show_api_doc` (never guessed large) and reuse that exact value on every page (Procedure step 7). Changing `page_limit` between pages shifts the offset window and skips or duplicates rows; an over-cap value raises a 422 validation error that names the limit.
- Filtering: one-criterion selection -> server-side filter parameters to avoid missed rows and wasted round-trips; after filtering, re-query the unfiltered collection and confirm the filtered ids match the records whose raw field values genuinely satisfy the stated threshold. Map the task comparator to a filter value before calling (min/max filters are inclusive, so 'over/more than N' -> min filter N+1; 'under/less than N' -> max filter N-1; 'at least N / N or more' -> min filter N; 'at most N / N or fewer' -> max filter N) and verify the direction (min vs max, >= vs >) against the unfiltered rows. Union/intersection or per-member conditions -> compute the keep set in Python from paginated source lists and cross-check against the full collection (see the multi-criteria reference).
- Filter values: take genre/category/status strings from the app's enumeration API and use them exactly as returned, preserving case; never guess spellings or casing. For enum-valued filter parameters that have no enumeration API (e.g. a `direction` filter), read the allowed values from `show_api_doc` — the parameter's `constraints` list them (e.g. 'sent'/'received') — and pass one of them verbatim; never guess a value like 'outgoing', which raises a 422 validation error that names the valid values and wastes a round trip.
- Per-record state flags: when the task's condition is a per-user state flag (liked, reviewed, downloaded, in_library, following) whose value the list/search row omits and whose API doc lists no filter for it, fetch it per record from the app's per-record private/state API (`show_<entity>_privates`) instead of guessing an unsupported filter parameter or inferring it from list position.
- Target selection: choose the record whose label/name/title field matches the entity the task names, never by time-of-day or list position. Match case-insensitively and treat hyphens/underscores as spaces, so a task naming "go-to-sleep" matches a record labelled "Go to sleep"; if no retrieved record's label matches, the list is incomplete — re-paginate or re-query the full collection before mutating. For a disable-the-rest task, derive the to-disable set from the fully-paginated list (`to_disable = [r for r in records if r['enabled'] and r['<id_field>'] != target_id]`) and disable exactly those records, never a fixed id list retyped from a glance.
- Field-scoped updates: update/PATCH APIs change only the fields you pass, so pass ONLY the field(s) the task actually changes (e.g. `time` to move an alarm, `enabled=False` to disable one) and re-read afterward to confirm every other field stayed identical; reconstructing the full record risks extra side effects that "only changed field" assertions flag.
- People references: when a task names people by relationship (coworker, friend, manager, family, roommate, ...), resolve them from the phone/contact app — never the target app's own social graph (`search_friends`/follower list), which counts a different set — and never guess names or emails. Load the people look-up procedure (Procedure step 6) to enumerate every relationship, union the results, and match the full set against the target app's sender/receiver fields.
- Credentials: take identity and passwords only from supervisor APIs (`show_profile`, `show_account_passwords`); never invent them.
- Dates: obtain current date/time from `datetime.now()` or the phone/clock API, never from memory. App record timestamps (`created_at`, `updated_at`, `approved_at`, `denied_at`) are naive ISO strings with no timezone suffix, so parse them with `datetime.fromisoformat(...)` and compare against a naive `datetime.now()` — never `datetime.now(timezone.utc)`, whose timezone-aware datetime raises `TypeError: can't compare offset-naive and offset-aware datetimes` when compared with a record timestamp. The phone clock's `get_current_date_and_time()` returns a human-readable `date` like `'Thursday, May 18, 2023'` (format `'%A, %B %d, %Y'`) and a 12-hour `time` like `'12:00 PM'` — parse it with `datetime.strptime(now['date'], '%A, %B %d, %Y')` or simply use `datetime.now()`, which already returns a datetime; never assume a `'%Y-%m-%d'` format. Compute every relative-date window ('yesterday', 'last N days', 'last month') from the fetched/parsed date via `timedelta`, never by hardcoding a literal date. 'last N days (including today)' spans N calendar dates: `min_date = today - timedelta(days=N-1)` and `max_date = today` — subtract N-1, not N, or you over-include an extra day. When selecting or bucketing by a relative month/year ('last month's bill', 'files from February and March of this year'), anchor the phrase to the current date first and compare the full year-month (never the calendar month alone) — a same-month record from a different year is out of scope and belongs to the fallback/other bucket. When comparing a record's timestamp to a computed cutoff, parse the record value with `datetime.fromisoformat(row['<created_at_field>'])` and compare datetimes — never compare ISO timestamp strings lexicographically, because a tz-aware cutoff like `'2023-04-18T11:58:00+00:00'` and a tz-naive row value like `'2023-04-17T12:11:26'` only sort correctly while both happen to share one format.
- Time arithmetic: compute any time-of-day shift with `datetime` arithmetic (`strptime` -> `timedelta` -> `strftime`) and format back in the exact string format the update API documents, never by hand (see the time-shift reference).
- File paths: for a `~/...` path the task names, never assume `~` is `/home/admin` — discover how the file_system app represents the user's home and follow that convention for every path argument (see the file-export reference).
- Binary files: a file whose read/`show_file` `content` starts with `binary:` (PDF/JPEG/MP3 and other non-text types) has no readable text and no API can decode it — skip it for any content-reading or summing task and use the `.txt`/text files instead of trying to read or decode it.
- Output volume: never dump a whole high-cardinality result to stdout — list/search/feed rows AND recursive directory/list-all listings such as `show_directory`, which return the entire file tree, not one level. Keep results in a variable and print only what the next step needs: for list/search/feed, print `len(rows)` and the ids you will mutate; for directory discovery, print only the single matching home entry. A raw dump of hundreds of rows overflows context and stalls the run before the mutation.
- Irreversible actions last: run disruptive/destructive mutations (`delete_account`, `delete_file`) only after every dependent read/write and the final re-read verification, so the task never deletes data it still needs.
- Extra side effects: produce only the records the task's state change requires; never chain a preparatory mutation when the primary API already accepts the needed parameter (e.g. topping up a payment balance before sending money instead of passing the card on the send call). A top-up persists an extra account/bank-transfer record and can write a receipt file, failing the evaluator's model-changes assertion (see the send-money reference).
- Read-only question tasks: when the task only asks for a value computed from existing state (a sum, count, or selection), call ONLY read APIs (list/search/`show_...`). Never call `copy_file`/`create_file`/`delete_file`/`move_file`/`decompress_file` or any mutation API — each write persists a File/Directory record and fails the evaluator's `assert no model changes` check.
- Social-feed / own-item exclusion: a social or news feed lists only OTHER users' items — your own transactions, posts, or payments are excluded from it. When a question asks for a total or count 'including me/mine' over such a feed, sum the matching retrieved items and then ADD the task-stated own amount, never assuming your own item is already present in the feed.
- Variable naming: define each token, credential, and id under ONE canonical name and reuse that exact name in every later block. On a NameError, fix only the undefined name to the already-defined variable instead of re-logging in or re-fetching data already held.
- Aggregates from in-memory data: compute sums/counts from the already-fetched list variable (`sum(t['amount'] for t in rows)`, `len(rows)`), never by re-typing printed values into a new hardcoded list — a transcription typo silently changes the answer.
- Queue/playlist adds ('add every song/record matching <predicate> to my queue/playlist'): append each matching id exactly once through the queue's add API — never a play/replace API — and never touch the entries already queued. Re-read the queue afterwards and assert every target id is present AND the pre-existing entries are unchanged (same ids, same order).

## Error Patterns to Avoid
- Trailing-markup code blocks: appending a DSML/XML closing tag (e.g. `</...>`) or fullwidth bars to a code block raises `SyntaxError: invalid character` and the block runs nothing. Strip the tag line and resubmit only the Python.
- Repeating the same failing block many times without changing a line — change the code, not the attempt.
- Guessing `page_limit` above the API cap -> 422 validation error; changing `page_limit` between pages silently skips rows.
- Stopping after the first page of a paginated list/search/feed.
- Guessing filter strings instead of reading them from the enumeration API.
- Logging into a phone app with the email -> 401 "Invalid credentials"; print the login doc and use the account phone_number.
- Picking the first keyword-matching record without cross-checking its values/date -> acting on the wrong (decoy) record.
- Replying from the task's one-line wording instead of reading the actual incoming message.
- Writing a CSV with the `csv` module -> "Usage of the following function is not allowed"; wrapping CSV cells in double quotes -> the evaluator's plain split keeps a literal quote on every value and the comparison fails.
- Mutating without reading current state first -> duplicate or missing side effects that the evaluator flags.
- Finishing with a bare word like `completed` instead of `complete_task()`, leaving the recorded answer not_given.
- Passing a full-sentence answer, or passing an answer for a state-change task.

## Output Format
The final executed statement must be `apis.supervisor.complete_task()`. Question tasks: pass a minimal `answer` (an entity name or number, never a sentence). State-change tasks (follow, send, add, remove): omit `answer` so the recorded answer is `null`. Never end with prose or a bare word.
- Numeric answers: pass the bare number only — `answer="314"` or `answer=314` — with no currency symbol, no thousands separator, and no unit. The evaluator normalizes the answer with `float()`, so any non-numeric character (a leading `$`, a comma, or a `$314`-style string) breaks the comparison even when the value itself is correct.
