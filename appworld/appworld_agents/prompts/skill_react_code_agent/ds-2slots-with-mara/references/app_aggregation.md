# Aggregating a Numeric Field Over App Collections (sum/count question)

Use for read-only question tasks whose data lives in an app's list/search API or a social/activity feed, not in directory files: 'how many likes/plays/comments/views do all my <records> [that I sent/received] have in total [over <period>]?', 'what is the total <field> of my <records>?', or 'how much did <person> pay/receive in total for the others?'. The records are APP ENTITIES reached through a list/search API or a social feed (transactions, orders, payments, library items, feed entries); the answer is one bare number and the task is read-only. For records that are FILES in a directory, route to `references/file_aggregation.md` instead.

## 1. Print the list API doc first and pin the field plus filters
Print the target collection's list/search API doc before the first call. Read its response schemas and parameter list to map the question's words: the aggregate field the question names ('likes' -> `like_count`, 'plays' -> `play_count`, 'comments' -> `comment_count`; a 'how many X' count -> `len(rows)`), and the server-side filters that carry the task's predicates (direction, date range, status). Never guess field names, parameter names, or filter values.

If the field the question's predicate depends on is absent from the list/search row, do not treat a summary field as a stand-in: collection summaries often record when the item was added to the collection (`added_at`) rather than the entity's own date (a song's `release_date`). When the predicate names the entity's own date ('released'), fetch that field per record from the per-entity detail API (`show_<entity>`) once per record and evaluate the predicate on that detail value — never filter the library call on `added_at` and never pass a filter parameter the list doc does not list.

## 2. Anchor the period to the current date
Get the current date/time from `datetime.now()` or the phone/clock API, never from memory. Resolve the task's period to concrete date bounds computed from that date — never hardcode a year: 'this year' -> `min = f'{year}-01-01'`, `max = f'{year}-12-31'`; 'this month' -> first through last day of the current calendar month; 'last month' -> the previous calendar month. Pass the strings in exactly the format the doc specifies (usually `YYYY-MM-DD`).

## 3. Map the direction verb to the direction filter (or leave it unset when no side is named)
Decide from the question whether ONE side is in scope:
- The task NAMES a side ('transactions I sent/received', 'payments I made/received') -> pass the list API's `direction` filter with its documented value verbatim (e.g. `'sent'` / `'received'`). NEVER omit the direction here: summing both sides inflates (or under-counts) the answer.
- The task names NO side ('all my transactions', 'my payments this month') -> LEAVE the direction filter unset so both directions are returned. Filtering to one side silently drops the other half and under-counts the total.
- The task asks for a NAMED OTHER person's total ('how much did my manager pay for the others', 'how much did <person> receive for the <event>') -> resolve that person's identifier from the contact app (see `references/people_references.md`), then read WHO paid WHOM in the scenario sentence to decide which end of the app's rows the named person occupies — 'paid for' alone is ambiguous. Reimbursement pattern ('X paid for food and everyone venmoed X', 'X paid the bill and everyone paid X back'): the named payer is the RECEIVER of the others' repayments, so 'how much X paid for the others' equals the total the others paid X -> keep rows whose receiver identifier equals that person. Direct-payment pattern ('X venmoed/sent everyone their share', 'X paid each friend $N'): the named payer is the SENDER -> keep rows whose sender identifier equals that person. Sanity-check the chosen side against the rows: the correct side shows the others (relationship-resolved people minus the named person and minus yourself) on the opposite end, so a side with zero matches means you picked the wrong direction (a reimbursed payer is the RECEIVER, not the sender). Never substitute a venue/description keyword for the person's identifier — an unrelated same-venue event would corrupt the total. When the question also says 'including me/mine' over a social feed, sum the matched rows and then ADD the task-stated own amount (feeds exclude your own items — see the SKILL.md social-feed / own-item exclusion rule).
If the doc lists no direction parameter, fetch all rows and keep only those whose sender/receiver/owner identifier equals your own (from `show_profile`): 'I received' -> keep rows whose receiver identifier is mine; 'I sent' -> keep rows whose sender identifier is mine.

## 4. Fetch fully paginated and sum the named field
Loop `page_index` from 0 with ONE explicit `page_limit` copied from the doc (reuse the same value on every page; stop when a page returns fewer than `page_limit` items or is empty). Accumulate the mapped field over the rows: `total = sum(r['<count_field>'] for r in rows)` for a field sum, `total = len(rows)` for a count. Print `len(rows)`, a compact per-row breakdown of the summed values (row id + field value) alongside the running total, so a dropped page or a wrong field is visible before answering.

When the question spans multiple named collections ('across my A and B libraries'), fetch EACH named collection fully paginated (omitting one silently drops candidates), expand every nested child-id list into one candidate set (an album/playlist library row exposes `song_ids`), and count the UNION of distinct ids — `len(set(candidate_ids))` — never the sum of per-collection counts. The same entity recurs across collections (a song can sit in both the song library and an album-library album), so summing per-collection counts double-counts the overlap and inflates the answer; print each collection's id set and the overlap before answering.

## 5. Verify scope, answer bare, then stop
Before answering, re-check each row is in scope: its date field falls inside the window and, for 'my records' tasks, the row involves the user (sender/receiver/owner equals the user's own identifier), so foreign rows never leak into the total. For a named-person total, prove completeness too: the rows you keep must show the contact-resolved contributor set (relationship-resolved people minus the named person and minus your own email) on the end opposite the named person — the senders for a reimbursement-pattern total, the receivers for a direct-payment total — so each expected contributor appears exactly once; if any is missing, a page was dropped or the feed is incomplete, so re-paginate and re-filter before summing an under-count. Then call `apis.supervisor.complete_task(answer=<bare number>)` — digits only, no currency symbol, thousands separator, or unit. Use only read APIs throughout; any write API call persists a record and fails the evaluator's `assert no model changes` check.
