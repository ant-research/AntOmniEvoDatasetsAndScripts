## Overview
Complete AppWorld tasks by writing Python code that interacts with app APIs through the `apis` object, then marks the task done via `apis.supervisor.complete_task()`.

## Procedure

1. Read the task instruction. As the FIRST lines of your first code block, set `task_type = 'action'` or `task_type = 'question'` and (if relationship terms appear) `relationship_terms = ['<term1>', ...]` and (if relative time appears) `target_date = datetime.datetime.now() - timedelta(days=N)`. Classify as **question task** (asks for a count, name, list, or comparison) or **action task** (asks to add, follow, create, delete, remove, send, update, or perform an operation without asking a question). If the instruction references people by relationship term (friend, coworker, family, roommate, manager, etc.), list ALL distinct terms mentioned — e.g., 'my coworkers and my manager' yields ['coworker', 'manager']. You MUST resolve each term via `resolve_relationships` (step 2), never via the target app's own friend/follow API. Missing a term silently omits those contacts from the contact set. If the instruction references a relative time (yesterday, today, this week, last month, etc.), compute the target date programmatically: `from datetime import datetime, timedelta; current_date = datetime.datetime.now(); target_date = current_date - timedelta(days=1)  # for 'yesterday'`. For 'last N days including today', today counts as the first day — subtract (N-1) days and zero the time: `target_date = (now - timedelta(days=N-1)).replace(hour=0, minute=0, second=0)`. Store `target_date` as a variable and use it in all subsequent filtering logic — never hardcode a derived date as a string literal (e.g., `yesterday = '2023-05-17'`), because manual derivation is error-prone and fragile across tasks with different current dates.
   Gate: if the task mentions relative time, `assert 'target_date' in dir(), 'Relative time reference detected — compute target date via timedelta before proceeding'`; `assert 'task_type' in dir() and task_type in ('action', 'question'), 'task_type must be set to action or question before proceeding'`; if the task mentions relationship terms, `assert 'relationship_terms' in dir() and len(relationship_terms) > 0, 'Relationship terms detected — list all terms before proceeding'`
2. Look up credentials and login using the helper. First, define `SKILL_DIR` using the path from the Skill Resources section: `from pathlib import Path; SKILL_DIR = Path('<path from Skill Resources>')`. Load the helper: `exec((SKILL_DIR / 'scripts/helpers.py').read_text())`. Call `login_to_app('<app_name>')` for each app — the phone app is auto-detected (no `username_field` needed). Store the returned `profile` dict and use `profile['email']` or `profile['phone_number']` in all subsequent logic, never hardcode these values.
   Gate: `token, profile = login_to_app('<app_name>'); assert token, 'Login must succeed'` — never write string literals for username or password in login calls; `login_to_app` handles credential lookup programmatically.
   If step 1 identified relationship terms, also login to the phone app: `phone_token, _ = login_to_app('phone')`. Then call `resolve_relationships` from `scripts/helpers.py` (already loaded): `contact_ids, contacts = resolve_relationships(relationship_terms, phone_token)` where `relationship_terms` is the list from step 1 (e.g., `['friend']` or `['coworker', 'manager']`). Gate: `assert contact_ids, 'Contact set must be non-empty before filtering target app data'` — use `contact_ids` (a set of emails) to filter records in the target app. Never call the target app's friend/social API (e.g., `venmo.search_friends`, `spotify.search_friends`) to resolve relationships — those return platform connections, not contacts by relationship. `resolve_relationships` handles the correct lookup via `phone.search_contacts` automatically.
3. For each API call needed, check the API doc if unsure of parameters: `apis.api_docs.show_api_doc(app_name=..., api_name=...)`.
4. When the task involves replying to a person or acting on a request received via messages, read the relevant conversation history first (e.g., `get_all_pages(apis.phone.show_text_message_window, access_token=phone_token, phone_number=...)`, `get_all_pages(apis.gmail.show_email, ...)`). Wrap these calls in `get_all_pages()` — conversation history can span multiple pages, and a bare call silently omits earlier messages that contain the actual constraints or amounts. Task instructions may reference "their request" without restating details — the specific constraints only appear in the conversation.
5. Execute API calls, paginating all list endpoints. `SKILL_DIR` should already be defined from step 2; if not, define it now. Load the pagination helper: `exec((SKILL_DIR / 'scripts/pagination.py').read_text())`. Call `get_all_pages(api_func, **kwargs)` for every list/search API — never call a list API directly (a bare call with `page_index=0` always misses later pages). Collect ALL pages into a single list before computing.
   Verify: (1) every `show_*`, `search_*`, or `list_*` API call in your code is wrapped inside `get_all_pages()` — a bare call like `apis.spotify.search_albums(query=...)` silently truncates results; (2) `get_all_pages` is the only place `page_index` and `page_limit` appear as arguments.
6. Perform the required actions or compute the required answer using the fully collected data. Always extract values from API responses programmatically — never hardcode IDs, names, or values observed in printed output into variables. When items contain multiple instances of a target entity (e.g., multiple artists in a song, multiple recipients in a payment), iterate ALL instances to collect the complete set — taking only the first or primary instance silently omits entities, producing incomplete mutation sets for action tasks and wrong counts for question tasks. When looking up a specific entity by name from search results, use `find_entity` from `scripts/pagination.py` (e.g., for an artist: `artist = find_entity(apis.spotify.search_artists, 'name', 'Lily Moon', query='Lily Moon')` then use `artist['artist_id']`; for a contact: `contact = find_entity(apis.phone.search_contacts, 'first_name', 'Kristin', access_token=phone_token, query='Kristin')` then use `contact['phone_number']` and `contact['email']`) instead of printing results and hardcoding values. When data is already in a variable from a prior step, filter and extract programmatically from that variable — never print then transcribe (e.g., `joseph = [c for c in contacts if c['first_name'] == 'Joseph'][0]; joseph_phone = joseph['phone_number']; joseph_email = joseph['email']` instead of printing contacts then writing `joseph_phone = '2233697879'`). For other extractions, write code that parses API output (e.g., `song_ids = [s['id'] for s in album['songs']]` instead of `song_ids = [37, 38, 39]`). When a task requires an amount or value from text content in any app — conversation messages, file content, note content, or document text — parse it programmatically: from message text (e.g., `import re; match = re.search(r'\$(\d+)', message_text); amount = float(match.group(1))`), from file or note content (e.g., `match = re.search(r'Total Amount.*?\$(\d+)', content); amount = float(match.group(1))`), or from structured content using the appropriate parser (`yaml.safe_load()` for YAML, `json.loads()` for JSON) — instead of hardcoding it (e.g., `amount=54.0`) or mentally computing and hardcoding derived values (e.g., `2700` instead of `duration_mins * 60`). For "least/most" questions, read `references/question_patterns.md` for the computation pattern.
   Gate: before executing any API call that takes an entity ID or name argument, any file system read call, or calling complete_task, verify no argument is a string or number literal that duplicates a value from earlier printed output — all identifiers, amounts, addresses, answer values, and file paths must be variables assigned from API response fields, computed in prior steps, or parsed from message, file, or app text content (never re-derived from printed output in a new arithmetic expression, e.g., `answer=77+70+86+77` instead of `answer=total_cost`). Also verify any numeric threshold or comparison value in filtering logic is a variable computed from prior steps or parsed from text content, not a hardcoded number derived from manually reading output (e.g., `>= 2700` is wrong if 2700 was mentally computed from printed note content; use `>= required_duration` where `required_duration` was parsed programmatically). File paths from `show_directory` output must be filtered in code, never transcribed as string literals. Entity IDs and names in detail API calls (e.g., `show_note(note_id=3016)`, `show_song(song_id=5)`) must be variables extracted from prior search/list results, not literals transcribed from printed output.
   Gate (file system): `assert not any(isinstance(arg, str) and arg.startswith('/') for arg in [locals().get('file_path'), locals().get('directory_path')]), 'File path must be a variable from programmatic filtering, not a hardcoded string literal'`
7. Verify each action with a follow-up read call before calling complete_task (e.g., after sending money, confirm via transaction history; after sending a text message, confirm via message history; after following an artist, confirm the follow succeeded). For bulk mutations on multiple records, re-fetch the affected list and confirm ALL target records reflect the change — verifying only one record cannot detect silent failures on others. Skipping verification risks reporting success for an action that silently failed.
   Gate: after each mutation API call and before complete_task, at least one read API call must confirm the action succeeded (e.g., check transaction record, message history, or follow status). For bulk mutations on N records, the verification must cover all N — re-fetch the affected list and assert each target ID appears with the expected change.
8. Call `apis.supervisor.complete_task()` as the final step:
   - **Question tasks**: pass `answer=<value>` — keep answers minimal (entity names, numbers, sorted lists), not full sentences.
   - **Action tasks**: omit the `answer` argument entirely. Never pass a count or summary as the answer.
9. Gate the `complete_task` call using `task_type` from step 1. Write it as a conditional: `if task_type == 'action': apis.supervisor.complete_task()` (no `answer` keyword) `else: apis.supervisor.complete_task(answer=<value>)`. Never pass `answer=` for action tasks — passing a count like `answer=1` causes test failure even when all operations are correct.
   Gate: before calling complete_task for a question task, `if isinstance(answer, float) and answer == int(answer): answer = int(answer)` — whole-number answers must be int, not float (e.g., `answer=310`, not `answer=310.0`).

## Rules

- **Pagination**: All list/search APIs require pagination. Load `scripts/pagination.py` and use `get_all_pages()` for every list/search call — never call a list API directly, because omitting pagination silently returns incomplete results. The API rejects any `page_limit` above 20 with a 422 error. Read `references/pagination.md` for why pagination matters.
- **Credentials**: Never hardcode or guess credentials. Use `login_to_app` from `scripts/helpers.py` (step 2) to handle credential lookup programmatically.
- **Access tokens**: Store the access token from login and pass it to all subsequent API calls that require it.
- **Reply context**: Before replying to a message or conversation, always read the existing conversation first. Task instructions give vague summaries ("Laura asked for movie recommendations"), but the actual request may contain specific constraints ("from Quentin Tarantino") only visible in the conversation. Skipping this leads to unfiltered responses that fail constraint checks.
- **Pre-mutation state check**: Before performing bulk mutations (follow multiple artists, add multiple contacts, download songs, etc.), use `compute_new_items` from `scripts/pagination.py` to find items not already present — only act on the returned list. Example: `new_ids = compute_new_items(apis.spotify.show_downloaded_songs, 'song_id', target_ids, access_token=token)` then `for id in new_ids: download_song(...)`. This avoids 422 'already exists' errors from duplicate operations that cause test failures in apps that reject operations on existing records.
- **Verification**: After performing an action (follow, create, delete, send, update), call a read API to confirm the action succeeded before calling `complete_task`. For bulk mutations (affecting multiple records), re-fetch the full list via `get_all_pages` and verify every target record shows the expected change — confirming only one record risks missing silent failures on the rest.
- **Minimize side effects**: When performing an action, prefer the most direct API path. Evaluation checks model changes against expected records — intermediate state (e.g., BankTransfer from adding to Venmo balance before sending) causes test failures. If a direct call fails with one candidate value (e.g., one payment card), try all remaining candidates before resorting to indirect approaches that create extra model changes.
- **Minimal message content**: When composing messages via API (text messages, emails, etc.), include ONLY the content the task specifies — no greetings, prefixes, explanations, or conversational framing. If the task says 'a list of comma-separated movie titles', the message body is just that list. Extra words can accidentally match substrings that fail constraint checks (e.g., 'Here' contains 'her' matching a movie title that should not appear).
- **Current time**: Obtain via `datetime.datetime.now()` (preferred — returns a datetime object with `.year`, `.month`, `.day` directly accessible; note: `datetime` is the module, so use `datetime.datetime.now()`, not `datetime.now()`) or `apis.phone.get_current_date_and_time()` (returns a dict with `date` in a non-ISO format like `'Thursday, May 18, 2023'` requiring custom parsing), never from internal knowledge. Store the current date in a variable (`now = datetime.datetime.now()`) and compute all relative dates from it in code using `timedelta` — never hardcode a derived date after reading the current date output. For example: `yesterday = (now - timedelta(days=1)).replace(hour=0, minute=0, second=0); this_year = now.year; this_month = now.month`. Deriving dates mentally and typing the result (e.g., `datetime(2023, 5, 17)`) is the same as hardcoding — it breaks when dates cross month/year boundaries. Use the stored date variable in all conditional logic and API filter parameters (e.g., `min_created_at=start_of_month.isoformat()`, not `min_created_at='2023-05-01T00:00:00'`). Never manually type date strings derived from printed output into API calls — always construct them from stored date variables.
- **Detail APIs for missing fields**: List APIs (show_*_library, search_*) return summary records that often lack fields needed for computation (e.g., play_count, price, duration, release_date). Before filtering or computing on a field from list results, verify the field is present in the first record: `assert list_results[0].get('FIELD') is not None, 'FIELD absent from list results — use detail API instead'`. If the field is absent from summary records, call the corresponding detail API (show_song, show_product, etc.) for each item. Filtering on an absent field silently yields 0 matches — the agent incorrectly concludes no items match when the field simply isn't in the summary.
- **Nested entity detail lookup**: Container records (albums, playlists) hold nested item IDs (e.g., `song_ids`), not full child records with all attributes. When a task asks about an attribute of items inside containers (e.g., 'most-played song in my album library'), extract the child IDs, deduplicate with a set, then call the child's detail API (e.g., `show_song`) for each — never assume the container record or its own detail API (e.g., `show_album`) provides child attributes like play_count or duration. This applies to both single-container tasks (just albums or just playlists) and multi-collection tasks ('across' or 'from all' albums + playlists): collect item IDs from every listed source, deduplicate, fetch child details, then compute. When fetching details, call the detail API for the target entity type (e.g., `show_song` for songs), NOT the container's detail API — container properties (album release_date) are not valid proxies for child-item properties (song release_date). Always use the detail API of the entity whose attribute the task asks about. Using container attributes as proxies for child attributes, skipping deduplication, or missing a source produces wrong results.
- **Nested entity extraction**: When extracting entities from a nested collection (e.g., all artists in a song, all items in an order), always iterate ALL nested items — not just the first. A contributing artist may appear as a non-primary entry; skipping them causes incorrect membership checks (e.g., wrongly unfollowing an artist who contributed to a liked song). Use `for item in parent['children']`, not `parent['children'][0]`.
- **Case-insensitive string filtering**: When filtering records by a string attribute (genre, category, type, status, label), always compare case-insensitively (e.g., `song['genre'].lower() == 'classical'`). API responses may store values in any case — a case-sensitive match silently misses records and produces incomplete results.
- **Threshold-based selection**: When a task requires selecting an item that meets a numeric threshold (e.g., "enough songs for a workout" means total duration >= required minutes, "within budget" means total price <= budget), compute the actual aggregate metric for each candidate — fetch detail records for nested items, sum or aggregate the target field, then compare to the threshold programmatically. Never use proxy heuristics (item count as a proxy for total duration, etc.) — proxies can silently fail when items vary in the target attribute. Compute before acting, not after.
- **Relationship resolution**: When a task mentions people by relationship (coworker, friend, family, roommate, etc.), use `resolve_relationships(relationship_terms, phone_token)` from `scripts/helpers.py` — it calls `get_all_pages(apis.phone.search_contacts, relationship='<term>')` for each term, returning a set of emails and the full contact list. Never call the target app's friend/social API (e.g., `venmo.search_friends`) to resolve relationships — those return platform connections unrelated to the contact-relationship meaning. The phone app's contact list is the authoritative social graph. `resolve_relationships` handles pagination and deduplication automatically; use the returned `contact_ids` (email set) to filter records in the target app programmatically.
- **Cross-app data reconciliation**: When a task requires matching data between apps (e.g., checking who paid against a list of shares), write programmatic matching logic — never manually compare outputs and hardcode the result. Parse one app's data into a dict/set, extract matching records from the other app, and compute the difference in code.
- **Account existence filtering**: When a task filters people by whether they have an account on an app (e.g., 'roommates without a venmo account'), login to that app and search for each contact's email using its user search API with `get_all_pages`. Contacts found in results have accounts; those absent across all pages do not. Email is the consistent cross-app identifier. Do not use app-specific social APIs (e.g., `search_friends`) which return platform connections, not account existence.
- **Ownership disambiguation ("my" collections)**: When a task says "my" playlist, album, or other personal collection, use the user's library API (e.g., `show_playlist_library`, `show_album_library`, `show_song_library`) to find it — not a global search API. Multiple users can own items with the same name; `search_playlists` returns all of them, and picking the first matching title silently selects another user's item. Library APIs return only the logged-in user's own items, eliminating this ambiguity. If a library API is unavailable and a search must be used, filter results by owner matching `profile['email']` — never assume the first name match belongs to the logged-in user.
- **File system**: When a task mentions "file system", "~/", or file/directory paths, use the `apis.file_system` app — not os/pathlib (which are disabled). Login with supervisor credentials, programmatically list and filter directories, then read files. Never hardcode file paths after viewing a directory listing. When filtering by year, use the `current_year` variable from step 1 (e.g., `f'/{current_year}-'`), not a hardcoded year string. Read `references/file_system.md` for the workflow.

## Error Patterns to Avoid

- **Passing an answer for action-only tasks**: If the task says "Add", "Follow", "Create", "Delete", "Remove", "Send", "Update", or any imperative verb without asking a question, do NOT pass an `answer` to `complete_task`. Passing a count or sentence like `answer="1"` or `answer="Followed 3 artists"` causes a test failure even when all operations are correct. The `answer` field must be absent or None.
- **Using page_limit > 20**: All paginated APIs enforce a maximum page_limit of 20. Values above 20 cause a 422 validation error. Always start with 20 or less.
- **Not paginating list APIs**: A single call to a list/search API does NOT return all results. When `len(results) == page_limit`, more pages exist — keep calling with incremented `page_index` until a page returns fewer than `page_limit` results. Missing this silently omits data.
- **Computing on partial paginated data**: Do not analyze or count results from a paginated API until all pages are fetched. Computing on the first page before checking remaining pages can produce wrong rankings or counts when later pages shift the result. Complete the full pagination loop first, then compute.
- **Missing a data source**: Tasks that mention multiple collections (e.g., "songs from my library, albums, and playlists") require querying each listed endpoint. Omitting one source silently yields wrong answers.
- **Manual data transcription**: Hardcoding values from API responses into code (e.g., `vacation_spots = ['athens', 'maui']` after reading a directory listing, or `users_to_find = ["Stephen", "Sabrina"]` after reading search results) produces correct results only by luck — you can mistype, miss items, or fail when data changes. Always write code that parses API output programmatically to extract the needed values: filter lists, extract subdirectory names, map IDs, etc. This applies whether the data comes from one API or multiple. The temptation is highest after an API error — when a call fails (insufficient balance, missing parameter, expired resource) and you query for alternatives, still parse and filter the results in code rather than copying an ID from printed output. For example, after getting an 'expired card' error, filter `payment_cards` for cards with `expiry_year > current_date.year or (expiry_year == current_date.year and expiry_month >= current_date.month)` and use `valid_cards[0]['payment_card_id']`, not a hardcoded integer.
- **Forgetting complete_task**: The task is not done until `complete_task` is called. Code that runs without errors but never calls `complete_task` fails.
- **Guessing values**: Never guess credentials, IDs, dates, or API parameter values (e.g., enum values like `direction`, `status`, `type`). Always look up credentials via supervisor, and check API docs via `apis.api_docs.show_api_doc(app_name=..., api_name=...)` before calling any API you have not previously used in the current task.
- **Treating API date fields as datetime objects**: Date fields in API responses (e.g., `created_at`, `updated_at`, `start_date`) are ISO format strings like `'2023-02-14T20:19:51'`, NOT datetime objects. Calling `.year`, `.month`, or `.day` on them causes `AttributeError`. Always parse them first: `dt = datetime.datetime.fromisoformat(created_at)` or `dt = pendulum.parse(created_at)`, then access `dt.year`, `dt.month`, etc.
- **Skipping pagination for lookup searches**: When using a `search_*` API to find a specific item (e.g., `search_users(query=email)` to check account existence), still wrap in `get_all_pages()`. The search may return many partial matches that push the exact match to a later page. A bare `search_*` call only checks the first page and silently misses the actual match.

## Output Format

Call `apis.supervisor.complete_task()` as the final step:
- **Question tasks**: `apis.supervisor.complete_task(answer=<minimal_value>)` — answers must be minimal (entity name, number, sorted list), never full sentences. When a numeric answer is a whole number, pass it as an int (e.g., `answer=275`, not `answer=275.0`). When the answer is a comma-separated list, use `','.join(items)` (no spaces after commas) — this matches the expected format.
- **Action tasks**: `apis.supervisor.complete_task()` — no `answer` argument at all.
- **Impossible tasks**: `apis.supervisor.complete_task(status='fail')`.
